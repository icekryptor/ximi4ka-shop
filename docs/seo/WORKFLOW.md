# SEO ximi4ka.ru — алгоритм работы над материалом

Единая инструкция для любой сессии (человека или агента), которая подхватывает SEO-работу по магазину «Химичка».
Читай её целиком до первой правки. Если инструкция расходится с реальностью (файл переехал, команда не работает),
сначала исправь инструкцию отдельным коммитом, потом работай дальше.

Роли: **владелец** — тот, кто даёт команды в чате (решения, мёрж, прод, кабинеты). **Сессия** — ты.

## 1. Стоп-правила (нарушать нельзя)

1. **Мёрж в `main` = выкатка на прод** (автодеплой по ssh из GitHub Actions, job `deploy` после `ci`). Мёржить можно только
   по явной команде владельца в чате; одобрение в одной задаче не переносится на другую. Красный CI = не выкачено.
   Единственное исключение — мелкие правки по разделу 1.1.
2. **Прод-сервер, прод-БД и ssh — только по отдельной команде владельца.** Все серверные шаги выполняет владелец по
   `deploy/SEO-LAUNCH.md`; сессия готовит команды и читает присланный вывод. Допустимы публичные GET к
   `https://new.ximi4ka.ru` (read-only).
3. **На сайте стоит `Disallow: /`** (значение `site_settings.robots_txt` в БД, общее для `ximi4ka.ru` и `new.ximi4ka.ru`) до
   открытия для индексации. Не менять, не «чинить». Открытие — только по разделу «Открытие для индексации» в `deploy/README.md`
   и только после того, как `new.ximi4ka.ru` отдаёт 301 на апекс (шаг 5 `docs/seo/apex-switch-plan-2026-10.md`): иначе `new.`
   станет полным дублем апекса.
4. **Не выдумывать факты:** характеристики товаров, концентрации, комплектации, сертификаты, цены, сроки, отзывы, рейтинги,
   цитаты, контакты, реквизиты, адреса. Нет данных → поля нет, а вопрос уходит владельцу.
5. **Юридические тексты** (оферта, политика) переносить дословно; любая правка (например, подпись продавца) — только по
   решению владельца и с пометкой в PR.
6. **Отзывы и рейтинги — только настоящие** (WB, Ozon, письма, Telegram, с разрешения). Разметку `aggregateRating`/`Review`
   включать, когда они есть в данных.
7. **Миграции БД** — отдельный особо осторожный сценарий (раздел 6.2). Без явного ТЗ миграции не писать.
8. **Контент без вычитки не публиковать.** Тексты, написанные сессией, — черновики (`draft: true`, `isPublished: false`).
9. **Instagram и Meta:** упоминание на сайте в видимом тексте требует юридической пометки по российскому закону; в разметке
   `sameAs` пометка не нужна. В футер без решения владельца не добавлять.
10. **Секретов в репозитории нет** (репозиторий публичный): ни ключей, ни токенов, ни ИНН, ни паролей, ни ID внутренних документов.

### 1.1 Мелкие правки: без согласования, вплоть до мёржа (решение владельца от 05.10.2026)

Мелкую правку сессия вносит сама: ветка от свежего `origin/main`, коммит, PR, мёрж после зелёного `ci`, затем read-only
проверка прода. Спрашивать у владельца не нужно; о сделанном сообщить в итоговом сообщении (со ссылкой на PR).

**Мелкая — только если выполнены все условия:**

- не меняет поведение сайта и API: опечатки и формулировки в документации и комментариях, форматирование, ссылки в доках,
  добавление статического проверочного файла или мета-тега подтверждения (Вебмастер, GSC, Bing);
- не больше 3 файлов и около 30 строк диффа, без новых зависимостей;
- все проверки раздела 6.1, шаг 4, пройдены с реальным выводом, `ci` на SHA PR зелёный.

**Мелкой не считается, даже если правка маленькая:** любой код middleware, роутинга, платежей, корзины, заказа, аналитики
покупок, авторизации и загрузок; миграции и сиды; тексты товаров, статей и лендингов (правило 8); юридические тексты
(правило 5); `robots.txt` и `Disallow` (правило 3); CI, деплой, переменные окружения; всё, где нужен прод-сервер или
прод-БД (правило 2). Правила 2–10 действуют без изменений.

Сомневаешься, мелкая ли правка, — она не мелкая: действуй по правилу 1. Деплои не накладывать друг на друга: следующий
мёрж только после завершения job `deploy` предыдущего. Если после выкатки прод-проверка не прошла — немедленно сообщить
владельцу, откат (revert-PR) без его команды не делать.

## 6. Алгоритмы по типам работ

### 6.1 Кодовая SEO-правка (цикл PR)

1. **Ветка от свежего `origin/main`**, осмысленное имя (`seo/<тема>`). Один PR — одна тема. Параллельным агентам — по
   отдельному worktree.
2. **`npm ci`** в корне. Next.js — читать документацию из `node_modules/next/dist/docs/` перед кодом.
3. **TDD:** тест на новое поведение, красный прогон, потом реализация. Для сидов и всего, что пишет в Postgres, тест должен
   проходить круг через реальную БД (jsonb переставляет ключи; сравнение через `JSON.stringify` ломается).
4. **Проверки перед PR** (все с реальным выводом, не «должно работать»):
   ```bash
   npm run lint && npm run typecheck          # корень
   npm run test -w web                         # если трогал web
   TEST_DATABASE_URL=postgres://…/свой_db npm run test -w api   # api — только на СВОЕЙ одноразовой БД
   npx prettier --check .                      # КОРЕНЬ: CI падает на format:check
   ```
   Общая тестовая БД `ximi4ka_shop_test` занята параллельными сессиями (TRUNCATE) и даёт ложные падения. Свою БД удалить после
   работы. Локальный pre-push хук прогоняет тесты, push долгий — это нормально.
5. **Коммиты и PR:** сообщения на русском в стиле `git log` (`feat(seo): …`, `fix(...)`, `docs(seo): …`), последняя строка
   коммита `Co-Authored-By: …` (как велит система), тело PR: Что / Зачем / Как проверено (команды и результат) / Что не вошло /
   Что сделать владельцу после мёржа; последняя строка тела — атрибуция Claude Code.
6. **Независимое ревью** для платёжно-смежного и затрагивающего данные кода (корзина, чекаут, заказ, аналитика покупок,
   загрузки): отдельным проходом code-reviewer и security-reviewer, не самим автором.
7. **Мёрж** (только по команде владельца): по одному PR; для каждого `gh pr update-branch N` → дождаться зелёного `ci` на новом
   SHA → `gh pr merge N --merge --subject "Merge PR #N: <название>"` (в репозитории принят merge-коммит) → дождаться, пока job
   `deploy` на main завершится → следующий. Конфликты разрешать в ветке PR слиянием `origin/main`, с прогоном тестов; не
   мёржить, если PR из стека (смени base на `main` после мёржа нижнего). Деплои не накладывать друг на друга.
8. **После выкатки** проверить прод read-only (раздел 3, шаг 3) и по результатам обновить память (раздел 9).

### 6.2 Миграции БД

Только добавление nullable-колонок и новых таблиц, без переименований и удалений; `ADD COLUMN IF NOT EXISTS`; тест up/down на
тестовой БД. Помни порядок деплоя: `deploy.sh` сначала переключает контейнеры, потом гоняет миграции, поэтому упавшая миграция
= новый код на старой схеме. Таблицы прод-базы принадлежат `ximishop_user`; если базу снова восстанавливали из дампа, владелец
мог стать `supabase_admin`, и ALTER упадёт с «must be owner». В PR описать: проверку владельцев, ручное добавление колонок от
superuser **до** мёржа, проверку после. Выполняет владелец. Образец — раздел «Блог: поля автора» в `deploy/README.md`.

### 6.3 Контент (карточки, категории, статьи, лендинги)

Конвейер: **кластер → бриф → черновик → вычитка → импорт → публикация → индексация → замер**.

1. **Кластер.** Выбери запросы из ядра («Химичка СЯ»): группа (ком — коммерческие, инф — информационные, смешанные, бренд),
   подгруппа, частота. Один кластер = одна посадочная страница; один запрос не ведёт на две страницы. Коммерческие кластеры →
   карточки товаров и категории; информационные → статьи, статья связывается с товаром (блок `product_grid`).
2. **Бриф.** Целевой URL, H1, ключи (естественно, без перечисления через запятую), структура, связанные товары, что нельзя
   утверждать. Факты о товаре — только из `api/data/tilda-catalog.json` и БД.
3. **Черновик.** Нормы: `metaTitle` ≤ 65 символов без суффикса бренда (« — Химичка» добавляет код), `metaDescription` ≤ 160,
   H1 60–80; title ≠ H1 дословно; уникальность ≥ 85%; «тошнота» ≤ 7%; водность ≤ 15%; без штампов («в современном мире»,
   «стоит отметить», «давайте разберёмся»); для реактивов обязателен раздел «Безопасность» (очки, перчатки, взрослые, малые
   количества, проветривание, хранение вне досягаемости детей, не пробовать на вкус) в осторожных общих формулировках. Запрещены:
   «безопасно для детей без присмотра», «лучшая цена», «гарантия», медицинские и юридические утверждения, инструкции по синтезу
   опасных веществ. Для статей — автор Василий Аистов (должность, био и фото не заданы), FAQ из 3–5 вопросов, 1–3 товара.
4. **Данные в репозитории** как JSON с флагом `draft: true`, импорт — идемпотентный сид, который **заполняет только пустые поля
   и никогда не перезаписывает** правки из админки. Тесты данных: длины, уникальность, существование slug товаров, запрещённые
   фразы. Статьи создаются `isPublished: false`.
5. **Вычитка владельцем** (факты, безопасность, привязки). Снимать `draft` и публиковать — после вычитки.
6. **Импорт** на сервере владельцем по `deploy/SEO-LAUNCH.md` (dry-run → боевой). После импорта текстов товаров **не запускать**
   `import:tilda-catalog`: он перезаписывает описания.
7. **Индексация:** добавить URL в Яндекс.Вебмастер («Переобход страниц») и GSC; убедиться, что страница в `sitemap.xml`, не
   `noindex`, отдаёт 200 и содержит канонический адрес апекса (после переключения).
8. **Замер** по 6.6 через 4–6 недель; страницы в индексе, но ниже топ-20, — на доработку (title, текст, перелинковка).

Шаблон страницы товара: H1, SEO-описание 300–500 слов (что это, для каких опытов, комплектация только из данных, безопасность),
FAQ 3–5 вопросов (разметка FAQPage), отзывы (когда есть), блок «Читайте также» со статьями и соседними товарами.

### 6.4 Серверные запуски

Выполняет владелец по `deploy/SEO-LAUNCH.md`: шаг 0 (предпроверки), 1 бэкап, 2 CMS-страницы, 3 картинки, 4 тексты товаров, 5 черновики
статей, 6 ручные шаги, 7 апекс, 8 откат. Роль сессии: подготовить точные команды, попросить вывод шага 0, по выводу решить, какие шаги
нужны, читать результат dry-run, помочь с откатом. В контейнере API нет `api/data` и `tsx`: файлы данных копируются `docker cp` в
`/app/api/data/`, сиды запускаются скомпилированными (`node api/dist/seeds/<имя>.js`). Не выдавать за проверенные команды
`docker` — они проверялись только локально без Docker.

### 6.5 Переключение апекса `ximi4ka.ru` с Tilda

Пошаговый план с окном 12.10.2026, подготовкой, откатом и рисками — `docs/seo/apex-switch-plan-2026-10.md`.

Условия (все): CMS-страницы `/policy`, `/oferta`, `/collab`, `/cert`, `/faq` отдают 200; карта 301 покрывает старые адреса (проверка
по выгрузке «страницы в поиске» Яндекс.Вебмастера и по счётчику редиректов в middleware); `NEXT_PUBLIC_SITE_URL=https://ximi4ka.ru`
и пересборка (переменная вшивается в сборку); блок Caddy для апекса и `www`, `www → апекс` 301; DNS (TTL заранее 300 с); готов
`robots.txt` для открытого сайта; картинки перенесены с Tilda (если подписку не продлят, они пропадут). Исполнение — раздел
«Открытие для индексации при переключении апекса» в `deploy/README.md`. После: ежедневно 7 дней смотреть ошибки индексации и 404,
отправить sitemap в Вебмастер и GSC, заполнить Яндекс Бизнес и Карты, подтвердить Bing Webmaster. Откат — возврат DNS.

### 6.6 Замеры и отчёт

Источники: Яндекс.Вебмастер (запросы, страницы в поиске, ошибки), Google Search Console, Яндекс.Метрика (визиты из поиска, цели,
ecommerce), Topvisor (позиции по ядру), Lighthouse по главной, категории, товару, статье, видимость в ИИ-ответах (ai.pixeltools).
Доступы у владельца; сессия просит выгрузки. Первая точка отсчёта фиксируется ДО переключения апекса.
Отчёт (раз в две недели и на замерах): что сделано (ссылки на PR), позиции и показы по небрендовым запросам относительно точки 0,
индексация (в индексе / в sitemap), ошибки, что в работе, что нужно от владельца. Цели Метрики (`add_to_cart`, `open_cart`,
`begin_checkout`, `purchase`) и «Электронная коммерция» заводятся владельцем вручную; для `purchase` не включать оплату за
конверсии в Директе, пока нет серверной сверки по вебхуку Т-Кассы (клиентскую цель можно подделать).

## 7. Если после выкатки что-то сломалось

1. Откройте лог job `deploy` и шаг «миграции»; сверьте с read-only проверкой прода (раздел 3, шаг 3).
2. Падение API блога или каталога после деплоя со схемой — почти всегда миграция/владелец таблиц (6.2).
3. Откат кода — revert-PR (по команде владельца, мёрж = деплой); откат данных — по разделу 8 `deploy/SEO-LAUNCH.md`.
4. Нестабильный тест в CI: перезапустить упавший job (`gh run rerun <id> --failed`), при повторе — разбираться как баг.

## 8. Известные грабли

- Тесты api на общей БД дают десятки ложных падений; своя `TEST_DATABASE_URL` на каждую сессию.
- `format:check` в CI падает на неотформатированных файлах: `npx prettier --check .` в корне перед PR.
- jsonb переставляет ключи: никаких сравнений через `JSON.stringify` для данных из БД.
- `import:tilda-catalog` перезаписывает описания и картинки значениями из JSON.
- Том `ximishop-uploads` не входит в ночной бэкап БД; после переноса картинок они лежат только там.
- Tilda отвечает 403 (ddos-guard) при быстрых запросах: пауза между GET, обход защиты не применять.
- Нестабильный тест `OrderStatusView` («покупка по заказу в статусе failed») замечен один раз в CI; перезапуск помог.
- Мёрж в `main` запускает ci и deploy; параллельные деплои не накладывать.
- Агент/сессия может завершиться без отчёта: проверять результат самому (`gh pr list`, файлы в ветке, CI).
