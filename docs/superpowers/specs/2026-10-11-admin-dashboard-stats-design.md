# Дашборд статистики в админке — дизайн

Дата: 2026-10-11. Ветка: `claude/admin-dashboard-stats-3586e7`.

## Цель

Страница в админке (`/admin`, сейчас там заглушка «Добро пожаловать») со сводкой и небольшим графиком. Период: неделя, месяц или свой диапазон. Метрики: клики, корзины, заказы, логины в ЛК, новые пользователи, сумма заказов.

Источник кликов и корзин — собственные события в БД (решение владельца). Яндекс.Метрику как источник не используем: у нас нет клиента Stats API, а токен рассчитан на Management API.

## Что есть в базе, а чего нет

Есть сейчас, новых таблиц не нужно:

- Заказы: `orders.created_at`, `status`, `total_rub`, `paid_at`, `deleted_at`.
- Новые пользователи: `customers.created_at`.
- Логины в ЛК: `customer_sessions.created_at`, по строке на каждый вход.

Нет: корзина живёт только в localStorage (`web/lib/cart.ts:40`), клики нигде не пишутся. События `add_to_cart` и `open_cart` уходят только в Метрику, прочитать их оттуда нечем. Поэтому нужны таблица событий, публичный приёмник и клиентский трекер.

## Данные

### Таблица `analytics_events`

Миграция `api/src/migrations/1790810000000-AddAnalyticsEvents.ts` (в проекте уже есть две миграции с ts `1790800000000`, берём больший). Формат как у соседних: класс `AddAnalyticsEvents1790810000000`, SQL через `queryRunner.query`, UUID по умолчанию `gen_random_uuid()`.

| Колонка       | Тип         | Примечание                                  |
| ------------- | ----------- | ------------------------------------------- |
| `id`          | uuid        | PK                                          |
| `type`        | varchar     | значение из белого списка                   |
| `occurred_at` | timestamptz | `DEFAULT now()`                             |
| `visitor_id`  | uuid        | случайный, из localStorage браузера         |
| `path`        | varchar     | путь страницы, обрезается до разумной длины |
| `meta`        | jsonb       | необязательный, ограничен по размеру        |

IP и User-Agent не сохраняются, в таблице нет данных, которые идентифицируют человека.

Индексы (все в той же миграции):

- `analytics_events (occurred_at, type)`: запрос кликов фильтрует только по периоду, поэтому ведущая колонка — время;
- `orders (created_at)` и `orders (paid_at)`: сейчас их нет, агрегаты по периоду без них будут сканировать таблицу.

Отдельный TypeORM-entity не заводим: таблицу пишут и читают только сырые запросы, источник схемы — миграция (`synchronize: false`).

### Типы событий (белый список)

`add_to_cart`, `open_cart`, `begin_checkout`, `material_lead`. Это те же цели, что уже уходят в Метрику (`web/lib/metrika.ts`). Событие `purchase` не пишем: заказ и так есть в `orders`.

## Приём событий

`POST /api/public/events`.

- Тело: `type` (из белого списка), `visitor_id` (uuid), `path`, необязательный `meta`. Валидация zod 4, как в остальных роутах; невалидное тело отклоняется.
- Ответ `204`. Запись в БД не блокирует и не ломает пользовательский сценарий.
- Rate-limit по IP на существующем хелпере (`api/src/routes/middleware/rateLimit.ts`). В тестах лимит поднимается переменной окружения, как у `LOGIN_RATE_LIMIT`.
- Известные боты по User-Agent отбрасываются на входе. Сам User-Agent не сохраняется.
- Роутер монтируется в `api/src/app.ts` рядом с остальными публичными.

## Трекер на витрине

`web/lib/track.ts`: отправка через `navigator.sendBeacon` (запасной вариант — `fetch` с `keepalive`). Ошибки глушатся, оформлению заказа и просмотру каталога трекер не мешает. `visitor_id` создаётся при первом событии и хранится в localStorage; недоступное хранилище не ломает страницу.

Точки подключения: места, где сейчас вызывается `reachGoal`:

- `web/lib/cart.ts:294-295` (`add_to_cart`, хук `useCart().add`);
- `web/components/CartDrawer.tsx:33` (`open_cart`);
- `web/app/[locale]/(public)/checkout/page.tsx:55` (`begin_checkout`);
- `get_materials/_components/MaterialsForm.tsx:59` (`material_lead`).

Если в `web/lib/metrika.ts` есть единая обёртка вокруг `reachGoal`, достаточно одной строки в ней. Условия вызова (например, нет счётчика Метрики) проверяются на этапе плана: события нашей аналитики не должны зависеть от наличия счётчика.

## API статистики

`GET /api/admin/stats?from=YYYY-MM-DD&to=YYYY-MM-DD`.

- Защита: `requireAdminAuth`, как у остальных админских роутов. Проверки роли в проекте нет, статистику видит любой админ.
- Валидация: zod, `from <= to`, период не больше 366 дней. Границы дней считаются по `Europe/Moscow` (`AT TIME ZONE`).
- Агрегаты — сырой SQL через `AppDataSource.query` (паттерн из `routes/admin/categories.ts`). В сырых запросах по `orders` обязательно `deleted_at IS NULL`.
- Ответ в формате `{ data }`, типы DTO лежат в `shared/src/types`.

### Определения метрик

| Метрика            | Как считаем                                                           |
| ------------------ | --------------------------------------------------------------------- |
| Клики              | события `add_to_cart`, `open_cart`, `begin_checkout`, `material_lead` |
| Корзины            | число уникальных `visitor_id` с `add_to_cart`                         |
| Заказы             | `orders.created_at` в периоде, без soft-deleted, все статусы          |
| Сумма заказов      | `SUM(total_rub)` по статусам `paid` и `shipped`, день по `paid_at`    |
| Логины в ЛК        | строки `customer_sessions` по `created_at`                            |
| Новые пользователи | `customers.created_at`                                                |

Ограничения, которые видны и в интерфейсе:

- «Логины в ЛК» — приближение: вход по уже живой сессии (в том числе SSO `/authorize`) строки не создаёт.
- «Новые пользователи» — только аккаунты ЛК; гость, который оформил заказ без входа, не считается.
- Корзины и клики копятся только с момента выкатки, истории за прошлое нет.

### Форма ответа

Итоги по периоду по всем метрикам плюс ряд по дням: для каждого дня `date`, `orders`, `revenueRub`. Дни без данных присутствуют в ряду с нулями, чтобы график не имел дыр.

## Страница (web)

Дашборд заменяет заглушку `web/app/admin/(authed)/page.tsx`.

- Серверный компонент, паттерн как у `orders/page.tsx`: cookie из `cookies()`, `cache: 'no-store'`, период в `searchParams`.
- Переключатель периода: «Неделя», «Месяц», «Свой период» (поля `from` и `to`). Чипы — по образцу фильтров заказов (`px-3 py-1.5 rounded-full`). По умолчанию неделя.
- Карточки: клики, корзины, заказы, сумма заказов, логины в ЛК, новые пользователи. Стиль `bg-white rounded-2xl border border-brand-border`, суммы через `formatRub` из `orders/orderUi.ts`.
- График выручки по дням на inline-SVG, без новых зависимостей (в `web/components/dataviz/` уже рисуют SVG руками). Тултип дня: дата, выручка, число заказов. Расчёт масштаба — чистая функция, отдельно от разметки.
- Пустой период и ошибка API показываются явным текстом, а не пустой страницей.
- Перед написанием кода: `web/AGENTS.md` требует сверяться с документацией Next 16 в `node_modules/next/dist/docs/`; в worktree зависимости не установлены, нужен `npm i`.

## Тесты

API (Vitest, `TEST_DATABASE_URL`, модель — `api/src/routes/admin-orders.test.ts`):

- приём событий: валидное, невалидный тип, невалидный uuid, слишком большой `meta`, бот, rate-limit;
- агрегаты на засеянных данных: границы периода по Москве, дни без данных, soft-deleted заказы исключены, выручка только `paid` и `shipped` по `paid_at`, уникальность корзин по `visitor_id`;
- `/api/admin/stats`: 401 без сессии, 400 на плохой период и на период длиннее 366 дней.

Web (Vitest, jsdom):

- чистая функция масштаба графика (в том числе нулевой максимум);
- `track.ts`: вызывает sendBeacon, молча переживает недоступный localStorage и ошибку сети;
- смоук страницы, как в соседних тестах.

`npm run lint`, `npm run typecheck`, тесты `api` и `web`, `npx prettier --check .` в корне, `/security-review` (публичный write-endpoint), визуальная проверка страницы в браузере.

## Выкатка

Мёрж в `main` = автодеплой в прод; миграция выполнится при старте. Мёржить и трогать прод-БД — только по явной команде владельца.

## Вне объёма

- сравнение с прошлым периодом;
- разбивки по товарам, источникам и UTM;
- очистка старых событий (добавим, если таблица вырастет: прикидку объёма делаем на этапе плана);
- экспорт в CSV;
- проверка роли для доступа к статистике;
- история кликов и корзин до выкатки.
