# Заказ в СДЭК после оплаты — дизайн (этап 4)

**Дата:** 25.09.2026. **Статус:** дизайн согласован по частям, ждёт просмотра спеки.
Общий план интеграции — `docs/plans/2026-09-23-cdek-delivery-design.md` (§5.4, §7).

## 1. Зачем

Сейчас оплаченный заказ заводят в ЛК СДЭК вручную по карточке в Telegram.
После этапа 4 заказ появляется в СДЭК сам — в том же формате, что заказ Тильды
№ 10325990882, — а менеджер видит номер и трек в админке и может повторить
создание одной кнопкой.

**Готово, когда:** оплаченный заказ с доставкой СДЭК за минуту-две появляется
в ЛК СДЭК с правильными отправителем, пунктом сдачи, местами и позициями; в
карточке заказа в админке виден номер СДЭК со ссылкой на трекинг; сбой СДЭК не
мешает оплате и не теряется — заказ повторяется сам, а после окончательной
ошибки ждёт кнопки «Создать в СДЭК ещё раз».

## 2. Решения (согласованы 25.09.2026)

| Вопрос              | Решение                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| Когда создаём       | При переходе заказа в `paid` — из вебхука Т-Кассы, сверки и кнопки «Отметить оплаченным»                      |
| Как                 | Своя очередь `cdek_shipments` + фоновый обработчик по образцу обработчика уведомлений                         |
| Формат              | Как у 10325990882: ИМ, тариф 136/137, сдача в `MSK310`, отправитель ИП Аистова, предоплата, «приложена опись» |
| Где виден результат | Только админка: статус, номер СДЭК, ссылка на трек, ошибка, кнопка повтора                                    |
| Telegram            | По СДЭК ничего не пишем. Ответы-статусы на карточку («оплачен», «отправлен», …) тоже убираем — см. §6         |
| Включение           | Флаг `CDEK_ORDERS_ENABLED`, по умолчанию выключен                                                             |

## 3. Эталон — заказ 10325990882

Снят через `GET /v2/orders?cdek_number=10325990882` 25.09.2026. Что берём как
правило (персональные данные получателя опущены):

- `type: 1` (интернет-магазин), `tariff_code: 136`, `shipment_point: "MSK310"`
  (Москва, пр-т Мира, 108), `delivery_point` — код ПВЗ получателя;
- `sender`: `company` «ИП Аистова Ксения Михайловна», `name` — ФИО, `email`,
  `phones[{number}]`; `seller.name` = `sender.company`;
- `delivery_recipient_cost: {value: 0}` — предоплата, у каждой позиции
  `payment: {value: 0}`;
- одно место: `number` «<id проекта>#<id заказа>», габариты коробки в см, вес в
  граммах = сумма весов позиций, `comment: "приложена опись"`;
- позиции: `name`, `ware_key` = артикул (`FECL3`, `CACL2-SOLV`, …), `cost` —
  цена за штуку, `weight` в граммах за штуку, `amount`;
- страховку (`INSURANCE`) СДЭК начислил сам по сумме `cost` — отдельно её не
  передаём.

## 4. Данные

### Очередь `cdek_shipments` (миграция)

| Колонка                    | Тип                  | Зачем                                           |
| -------------------------- | -------------------- | ----------------------------------------------- |
| `id`                       | uuid pk              |                                                 |
| `order_id`                 | uuid unique → orders | одна запись на заказ                            |
| `state`                    | varchar(16)          | `queued` · `registering` · `created` · `failed` |
| `attempts`                 | int default 0        | неудачные попытки в текущем окне                |
| `next_attempt_at`          | timestamptz          | когда обработчику снова взять запись            |
| `cdek_uuid`                | uuid null            | из ответа `POST /v2/orders`                     |
| `cdek_number`              | varchar(32) null     | номер СДЭК, он же трек                          |
| `last_error`               | text null            | последняя ошибка — показываем в админке         |
| `created_at`, `updated_at` | timestamptz          |                                                 |

Частичный индекс по `next_attempt_at` для `state in ('queued','registering')`.

### Места заказа

Разбивка по коробкам (`packCart`) сейчас считается на чекауте только для цены и
теряется. Сохраняем её в `delivery_address.packages` рядом с `quote` — тот же
смысл «расчёт на момент заказа», новой колонки не нужно. Для заказов,
оформленных до выкатки, разбивка пересчитывается из текущих данных товаров.

### Настройки (env, только на сервере)

| Переменная            | Пример / значение                    | Обязательна при включённом флаге |
| --------------------- | ------------------------------------ | -------------------------------- |
| `CDEK_ORDERS_ENABLED` | `true` / пусто                       | —                                |
| `CDEK_SHIPMENT_POINT` | `MSK310`                             | да                               |
| `CDEK_SENDER_COMPANY` | `ИП Аистова Ксения Михайловна`       | да                               |
| `CDEK_SENDER_NAME`    | ФИО из эталона                       | да                               |
| `CDEK_SENDER_PHONE`   | из эталона                           | да                               |
| `CDEK_SENDER_EMAIL`   | из эталона                           | нет                              |
| `CDEK_SELLER_NAME`    | по умолчанию = `CDEK_SENDER_COMPANY` | нет                              |

Тарифы — уже существующие `CDEK_TARIFF_PVZ` (136) и `CDEK_TARIFF_COURIER` (137).
В репозиторий попадают только заглушки в `api/.env.example` и
`deploy/app.env.example`.

## 5. Поток

1. **Постановка.** `saveOrderWithStatusEvent` при переходе в `paid` и доставке
   `cdek_pvz`/`cdek_courier` в той же транзакции вставляет `cdek_shipments`
   (`queued`, `ON CONFLICT (order_id) DO NOTHING`). Только при включённом
   флаге: иначе при включении в СДЭК уехали бы заказы, уже заведённые руками.
2. **Обработчик.** Тик раз в 10 с, одна обработка за раз внутри процесса (api —
   один контейнер, как у уведомлений), не больше 3 записей за тик. Внешний
   вызов — вне транзакции, результат пишется одной транзакцией.
3. **`queued` → POST.** Перед отправкой проверяем, что заказ всё ещё оплачен
   (`paid`/`shipped`); отменённый — `failed` с причиной «заказ отменён».
   - Если это не первая попытка, сначала `GET /v2/orders?im_number=<номер>`:
     если прошлый POST дошёл, а ответ потерялся, подхватываем найденный заказ
     (кроме записей в состоянии `INVALID`) и не создаём второй.
     «Не найдено» — 400 `v2_entity_not_found_im_number`, это не ошибка.
   - `POST /v2/orders` (тело — §5.1) → 202 с `entity.uuid` → `registering`.
4. **`registering` → опрос.** `GET /v2/orders/{uuid}` каждые 15 с:
   - `requests[CREATE].state = SUCCESSFUL` и есть `cdek_number` → `created`;
   - `INVALID` → `failed`, в `last_error` — тексты `errors[]` от СДЭК;
   - `ACCEPTED`/`WAITING` или нет номера — ждём дальше; если так больше 30 мин,
     считаем временной ошибкой (общее расписание пауз).

### 5.1 Тело `POST /v2/orders`

Собирается чистой функцией `buildCdekOrder(order, packages, config)`:

- `type: 1`, `number` = номер заказа (`XM-2026-00042`) — защита от дублей;
- `tariff_code` = `delivery_address.quote.tariffCode`, если нет — тариф из env
  по способу доставки;
- `shipment_point` из env;
- ПВЗ — `delivery_point` = `deliveryPointCode`; курьер — `to_location`
  `{code: cityCode, address, postal_code}`;
- `recipient`: `name`, `phones[{number}]` в формате `+7XXXXXXXXXX`, `email`,
  если есть. Телефон, который не приводится к `+7`, уходит как есть — СДЭК
  вернёт ошибку, она будет видна в админке;
- `sender`, `seller` из env; `delivery_recipient_cost: {value: 0}`;
- `packages[i]`: `number` = `<номер заказа>#<i+1>`, `weight`/`length`/`width`/
  `height` из разбивки, `comment: "приложена опись"`, `items` — позиции этого
  места: `name` из снимка заказа, `ware_key` = артикул (нет артикула — id
  товара), `cost` = цена за штуку, `weight` = вес товара в граммах, `amount`,
  `payment: {value: 0}`.

## 6. Telegram: только карточка нового заказа

Решение владельца: ответы-статусы в чате заказов мешают складу. После этапа 4:

- карточка нового заказа (`created`) остаётся как есть;
- события `status:*` больше не ставятся в очередь канала `telegram`; в Google
  Таблицу они по-прежнему уходят и обновляют строку;
- миграция удаляет ещё не отправленные записи `telegram` + `status:*`, чтобы
  после выкатки не пришёл хвост старых ответов;
- по СДЭК в Telegram ничего не пишем — ни успех, ни ошибку.

Это меняет решение «События в чат» из
`docs/superpowers/specs/2026-09-25-order-notifications-design.md` §2.

## 7. Ошибки и повторы

| Что случилось                                        | Что делаем                                                    |
| ---------------------------------------------------- | ------------------------------------------------------------- |
| Сеть, таймаут, 5xx, ошибка токена                    | повтор: 1 мин → 5 → 15 → 1 ч → 6 ч, окно 24 ч, потом `failed` |
| 429                                                  | пауза не меньше 30 с, попытка не засчитывается                |
| 4xx с `errors[]` на POST, `INVALID` при опросе       | сразу `failed` — повтор тех же данных бессмыслен              |
| Нет обязательной настройки (§4) при включённом флаге | обработчик не стартует, в лог — чего не хватает; записи ждут  |
| Флаг выключен                                        | обработчик не ходит в СДЭК, новые записи не ставятся          |

Расписание пауз и расчёт окна — общие с обработчиком уведомлений
(`nextDelayMs`, `retryWindowMs`), без копии.

## 8. Админка

В карточке «Доставка» страницы заказа — блок «СДЭК»:

- статус: «в очереди», «регистрируется», «создан», «ошибка»,
  «не создавался» (записи нет) или «автосоздание выключено»;
- номер СДЭК со ссылкой `https://www.cdek.ru/ru/tracking?order_id=<номер>`;
- при ошибке — `last_error`, число попыток и время следующей;
- кнопка «Создать в СДЭК ещё раз» — для `failed`, для `queued` с попытками
  (повторить сейчас) и для оплаченного заказа без записи. Для `created` и
  `registering` кнопки нет — иначе дубль.

Эндпоинт `POST /api/admin/orders/:id/cdek/retry` — под той же защитой, что
остальные действия (сессия + CSRF): создаёт запись или переводит её в `queued`
со сброшенными `attempts` и `next_attempt_at = now`. 409 — если заказ не
оплачен, доставка не СДЭК, запись в `created`/`registering` или флаг выключен.
Детальный ответ `GET /api/admin/orders/:id` дополняется `cdekShipment` и
`cdekOrdersEnabled`.

## 9. Безопасность

- Флаг `CDEK_ORDERS_ENABLED` выключен по умолчанию.
- Вне `NODE_ENV=production` обработчик отказывается создавать заказы на боевом
  `api.cdek.ru`: в `api/.env` лежат боевые ключи, и обычный `npm run dev` не
  должен заводить настоящие заказы. Разработка и живая проверка — на
  `api.edu.cdek.ru`.
- Реквизиты отправителя — только в env на сервере, в логи не пишутся.
- Данные покупателя уходят только в СДЭК; `last_error` виден только в админке.
- Перед выкаткой — `/security-review`.

## 10. Тесты

- `buildCdekOrder`: ПВЗ и курьер, несколько мест, товар без артикула,
  нормализация телефона; структура сверяется с эталоном §3.
- Обработчик на тестовой базе с фейковым клиентом СДЭК: успешный путь до
  `created`; сетевой сбой → повтор с паузой; 429 без счёта попытки; `INVALID` →
  `failed`; потерянный ответ POST → заказ подхвачен по `im_number`; заказ
  отменён до отправки; флаг выключен → записи нет; страховка от боевого URL
  вне production.
- Постановка: переход в `paid` из вебхука, сверки и админки ставит одну запись;
  повторный `paid` — no-op; `status:*` больше не попадает в канал `telegram`.
- Эндпоинт повтора: авторизация, CSRF, разрешённые и запрещённые состояния.
- Компонент блока «СДЭК» в админке.
- Живой прогон на `api.edu.cdek.ru` общей тестовой учёткой: создать заказ
  через обработчик и перечитать его `GET`.

## 11. Выкатка

1. Миграция и деплой с выключенным флагом — поведение магазина не меняется,
   кроме тишины в Telegram по статусам.
2. На сервере в `deploy/app.env`: реквизиты отправителя, `CDEK_SHIPMENT_POINT`,
   затем `CDEK_ORDERS_ENABLED=true`. Сервер трогаем только после отдельного
   согласия владельца.
3. Первый оплаченный заказ проверяем глазами в ЛК СДЭК против эталона.

## 12. Вне задачи

- Статусы доставки: вебхук `ORDER_STATUS`, поллинг, авто-«отправлен», трек на
  странице заказа покупателя — этап 5.
- Квитанции и этикетки — этап 6.
- Отмена или правка заказа в СДЭК при отмене у нас — вручную в ЛК СДЭК.
- Выпадающий список ПВЗ на чекауте — отдельная спека.
