# Трафик и точки роста в админке — дизайн

Дата: 2026-10-28. Ветка: `claude/website-traffic-organic-57a9e0`.

## Цель

Владелец открывает админку и, не заходя в кабинеты Метрики и Вебмастера, видит: сколько людей пришло и откуда, растёт ли
поиск (отдельно небрендовый), какие страницы собирают трафик без продаж и что конкретно сделать, чтобы поиска стало больше.

Критерии успеха:

- раздел «Трафик и рост» показывает данные на вчера; синхронизация идёт сама раз в сутки;
- цифры визитов по источникам за любой день совпадают с отчётом «Источники, сводка» в Метрике (та же модель атрибуции,
  без сэмплирования);
- клики и показы небрендовых запросов считаются по данным Вебмастера, бренд задаётся регулярным выражением в настройках;
- страница админки не ходит во внешние API: всё читается из нашей базы;
- сбой синхронизации не роняет api и не трогает витрину, а в админке видно, что и почему не обновилось;
- пока синхронизация выключена (нет токена или флага), мёрж ничего не меняет для покупателей;
- токенов нет ни в репозитории, ни в ответах API, ни в логах.

## Принятые решения

| Вопрос          | Решение                                                                                                   |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| Источники       | Яндекс.Метрика и Яндекс.Вебмастер. Google Search Console — отдельным этапом позже                         |
| Способ          | Ежедневная синхронизация всего в нашу базу (вариант B); админка читает только базу                        |
| Заказы          | Не копируются: выручка и заказы по страницам входа считаются на лету из `orders.attribution.last`         |
| Бренд / небренд | Регулярное выражение в настройках сайта, по умолчанию `химичк\|ximi4ka\|ximichka`; применяется при чтении |
| Доступ          | Новый токен `YANDEX_STATS_OAUTH_TOKEN` только на чтение; `METRIKA_OAUTH_TOKEN` конверсий не трогаем       |
| Включение       | `SEARCH_STATS_SYNC_ENABLED=true` и `NODE_ENV=production`, как у остальных воркеров                        |
| Кто видит       | Только роль admin                                                                                         |
| 404 на витрине  | Новый тип события `not_found` в существующей `analytics_events`, без отдельной таблицы                    |
| Графики         | Свой SVG по образцу `RevenueChart.tsx`; библиотеку графиков не добавляем                                  |

## Не входит в задачу

- Google Search Console, Topvisor, позиции по семантическому ядру из Google Sheet.
- Связка конкретного посетителя Метрики с заказом (ClientID в заказе) и воронка по отдельной странице.
- Цели и «Электронная коммерция» в кабинете Метрики — их заводит владелец; раздел от них не зависит.
- Уведомления в Telegram о падении трафика.
- Мобильная раскладка админки (её нет и у остальных разделов).

## Источники данных

Сверено с документацией Яндекса 28.10.2026. Пункты с пометкой «проверить» подтверждаются пробным запросом (задача 1 плана).

### Метрика, Reporting API

`GET https://api-metrika.yandex.net/stat/v1/data`, заголовок `Authorization: OAuth <token>`, право `metrika:read`.

- Параметры всех запросов: `ids=<счётчик>`, `accuracy=full` (без сэмплирования; в ответе проверяем `sampled=false`),
  `timezone=+03:00`, `limit=100000`, `date1`/`date2` в `YYYY-MM-DD`.
- Источники: измерения `ym:s:date`, `ym:s:lastsignTrafficSource`, `ym:s:lastsignSearchEngineRoot`; метрики `ym:s:visits`,
  `ym:s:users`, `ym:s:bounceRate`, `ym:s:pageDepth`. Значения источника: `organic`, `direct`, `referral`, `ad`, `social`,
  `internal`, `recommend`, `messenger`, `email`, `saved`, `qrcode`, `undefined`.
- Страницы входа: измерения `ym:s:date`, `ym:s:startURLPath`, `ym:s:lastsignTrafficSource`, те же метрики. `startURLPath` —
  путь без параметров, как `orders.attribution.landing`.
- Проверить: в 2026 году Яндекс менял модели атрибуции, и документация расходится в том, работают ли имена `lastsign*`. Если
  пробный запрос их не примет, используем `ym:s:<attribution>TrafficSource` с параметром
  `attribution=cross_device_last_significant`. Имена измерений и модель атрибуции — константы в одном файле.
- Проверить: в `data[].dimensions[]` есть `id` (код источника), а не только `name`.
- Квоты: 3 параллельных запроса, 200 за 5 минут, 5000 в сутки на пользователя. Синхронизация делает запросы строго по
  одному, их несколько в сутки. Превышение — 429 (в одной версии документации 420), обрабатываем оба кода.

### Вебмастер, API v4

База `https://api.webmaster.yandex.net/v4`, тот же заголовок, права `webmaster:hostinfo` и `webmaster:verify`. Токен
Вебмастера живёт 6 месяцев.

- `GET /user` → `user_id`; `GET /user/{user_id}/hosts` → ищем хост `ximi4ka.ru` и берём его `host_id`. Ничего не хардкодим;
  найденные значения кэшируем в памяти процесса.
- Запросы по дням: `POST .../query-analytics/list` с `text_indicator=QUERY`, `device_type_indicator=ALL`, `limit=500`,
  листаем `offset`. В ответе по каждому запросу `statistics[]{date, field, value}` с полями `IMPRESSIONS`, `CLICKS`,
  `POSITION`, `CTR`, `DEMAND` и `popular_complementary_indicator` — главный адрес по запросу. **Данные только за последние
  две недели**, поэтому история запросов копится с первого запуска; задним числом дальше двух недель её не получить.
  Проверить: как в теле задаётся период (документирован только `from`/`to` у фильтров).
- Итог по сайту по дням: `GET .../search-queries/all/history` с `TOTAL_SHOWS` и `TOTAL_CLICKS`. Глубину истории проверить
  пробным запросом.
- Индексация по дням: `GET .../indexing/history` (коды `HTTP_2XX`, `HTTP_3XX`, `HTTP_4XX`, `HTTP_5XX`, `OTHER`),
  `GET .../search-urls/in-search/history`, `GET .../search-urls/events/history` (`APPEARED_IN_SEARCH`,
  `REMOVED_FROM_SEARCH`), `GET .../sqi-history` (ИКС, год истории).
- Снимки адресов: `GET .../search-urls/in-search/samples` и `GET .../search-urls/events/samples`, `limit=100`, листаем
  `offset`. У событий есть `excluded_url_status` (причина: `NOT_CANONICAL`, `DUPLICATE`, `LOW_QUALITY`, `HTTP_ERROR`,
  `NO_INDEX` и другие).
- Ошибки: 404 `HOST_NOT_VERIFIED` / `HOST_NOT_INDEXED` / `HOST_NOT_LOADED`, 403 `INVALID_USER_ID`, 429 на
  `query-analytics` после 10 000 запросов в час.

### Наша база и витрина

- `orders.attribution.last.landing`, `paid_at`, `status`, `total_rub`, `deleted_at` — заказы и выручка по страницам входа.
- `analytics_events` (`type`, `visitor_id`, `path`, `occurred_at`) — шаги воронки `add_to_cart`, `open_cart`,
  `begin_checkout` и новое `not_found`.
- `${WEB_ORIGIN}/sitemap.xml` — список адресов sitemap для сравнения с индексом.

## Устройство

Модуль `api/src/lib/searchStats/`:

| Файл                | Назначение                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------- |
| `constants.ts`      | имена измерений Метрики, модель атрибуции, пороги точек роста, таблица ожидаемого CTR         |
| `metrikaReports.ts` | клиент Reporting API; `fetch` внедряется; 429/420 → `RateLimitError`, прочее → ошибка с кодом |
| `webmaster.ts`      | клиент Webmaster API; те же правила ошибок; поиск `user_id` и `host_id`                       |
| `sync.ts`           | `syncMetrika(range)`, `syncWebmaster(range)`, `syncSitemap()`; upsert в таблицы               |
| `worker.ts`         | `startSearchStatsWorker({env, clients, intervalMs})` по образцу `metrika/worker.ts`           |
| `growth.ts`         | чистые функции правил точек роста: на входе строки из базы, на выходе список находок          |
| `queries.ts`        | SQL для админки: источники, страницы входа с заказами, воронка, запросы, индексация, 404      |

**Расписание.** Воркер просыпается раз в час. Для каждого источника (Метрика, Вебмастер) смотрит последнюю успешную
запись в журнале: если её нет или она старше 20 часов — запускает синхронизацию этого источника. Перезапуск api не плодит
лишних запросов. Защита от наложения — флаг `running` в процессе, как у остальных воркеров.

**Окно.** Каждый запуск перезаписывает последние 7 полных дней (вчера и шесть дней до него): Метрика и Вебмастер
дописывают данные задним числом. Первый запуск (журнал пуст) берёт всё доступное: Метрику с 2026-10-01, запросы
Вебмастера — две недели, историю индексации и ИКС — сколько отдаст API (не дальше года).

**Порядок внутри Метрики:** источники, затем страницы входа. **Внутри Вебмастера:** `user_id`/`host_id`, запросы по
дням, итог по сайту, индексация, снимки адресов. Затем sitemap. Каждый шаг — отдельная транзакция; ошибка шага
записывается, следующие шаги того же источника пропускаются, другой источник идёт своим ходом.

**429.** Ждём `Retry-After` (не больше 5 минут) и повторяем один раз. Второй отказ — ошибка запуска; догонит следующий.
**401 и 403** не повторяем; в журнал пишем понятный текст: «токен отозван или истёк», «у токена нет права …».

## Таблицы

Миграции с отметкой больше `1790850000000`. Даты — московский день (`date`), числа — `integer` или `numeric(6,2)`.

| Таблица                  | Ключ                         | Колонки                                                                                                                 |
| ------------------------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `search_stats_sync_runs` | `id uuid`                    | `source` (`metrika`/`webmaster`), `started_at`, `finished_at`, `status` (`ok`/`error`), `error text`, `rows int`        |
| `traffic_sources_daily`  | `day, source, search_engine` | `visits`, `users`, `bounce_rate`, `page_depth`; `search_engine` = `''` для непоисковых источников                       |
| `landing_pages_daily`    | `day, path, source`          | `visits`, `users`, `bounce_rate`, `page_depth`                                                                          |
| `search_queries_daily`   | `day, query`                 | `shows`, `clicks`, `position`, `demand`, `top_url` (может быть пустым)                                                  |
| `search_totals_daily`    | `day`                        | `shows`, `clicks`                                                                                                       |
| `indexing_daily`         | `day`                        | `in_search`, `appeared`, `removed`, `http_2xx`, `http_3xx`, `http_4xx`, `http_5xx`, `http_other`, `sqi`, `sitemap_urls` |
| `index_page_snapshot`    | `kind, url`                  | `kind` (`in_search`/`excluded`/`sitemap`), `reason`, `title`, `last_access`, `event_date`, `captured_at`                |

- `index_page_snapshot` заменяется целиком по каждому `kind` в одной транзакции.
- `site_settings.brand_query_pattern varchar(300)` — регулярное выражение бренда; пустое значение = значение по умолчанию.
  Сохранение в админке проверяет, что выражение компилируется в Postgres (`'' ~* pattern`).
- `ANALYTICS_GOAL_TYPES` в `shared` пополняется типом `not_found`; срок хранения как у целей (чистится только `web_vital`).
- Индексы: ключи таблиц; `analytics_events (type, occurred_at)` уже есть.

## Страница «Трафик и рост»

`web/app/admin/(authed)/traffic/page.tsx`, серверный компонент по образцу главной админки; пункт меню в `NAV`
(`AdminShell.tsx`) с `adminOnly`. Период — `statsPeriod.ts` с пресетами неделя, месяц, 90 дней и свой.

Над блоками — «данные на вчера, обновлено …» или жёлтая плашка, если последняя успешная синхронизация старше 48 часов или
последний запуск с ошибкой (текст ошибки из журнала). Если данных за начало периода нет — «данные с …» (первый день, за который есть данные).

**Сводка «Точки роста».** По две лучших находки из каждого блока, всего не больше 7, одной фразой со ссылкой. Пусто —
«явных точек роста нет».

**Блок 1. Источники.** Столбики по неделям, сложенные по источникам; таблица источник → визиты → разница с прошлым
периодом; поиск разбит на Яндекс и Google; плитка «небрендовые клики Яндекса» (главный показатель `WORKFLOW.md`).

**Блок 2. Страницы, теряющие деньги.** Таблица страниц входа за период. Заказы и выручка — по
`attribution.last.landing`, оплаченные (`paid_at` не пуст, заказ не удалён). Метки:

- «трафик без продаж» — визитов ≥ 30 и 0 оплаченных заказов;
- «высокие отказы» — визитов ≥ 30 и отказов ≥ 40%.

Воронка по сайту: визиты (Метрика) → добавили в корзину → открыли корзину → начали оформление (уникальные `visitor_id`)
→ создали заказ → оплатили (`orders`). Подпись: шаги посчитаны разными системами, проценты между ними — ориентир.

**Блок 3. Запросы у порога топа.** Только небрендовые. Метки:

- «дотянуть до топа» — средняя позиция 4–20 и показов ≥ 10;
- «мало кликов» — позиция 1–3 и CTR < 3%: переписать title или description `top_url`.

Сортировка по потенциалу: показы × (ожидаемый CTR на целевой позиции − текущий CTR). Ожидаемый CTR — грубая таблица в
`constants.ts`: 1 место 28%, 2 — 15%, 3 — 10%, 4–5 — 6%, 6–10 — 3%, 11–20 — 1%; целевая позиция для «дотянуть» — 3.

**Блок 4. Индексация.** «В поиске N из M адресов sitemap (X%)» и ряд по дням; список адресов sitemap, которых нет среди
страниц в поиске; последние исключения с причиной; ответы робота 4xx и 5xx по дням; частые 404 за период с кнопкой «Сделать
редирект» → `/admin/redirects/new?from=<путь>` (форма редиректа заполняет поле из адреса).

Все пороги — константы в `constants.ts`.

## Витрина

- `web/app/not-found.tsx` получает маленький клиентский компонент, который один раз отправляет `trackEvent('not_found')`
  через существующий `web/lib/track.ts` (тот же фильтр ботов и лимиты). Других изменений витрины нет.
- Форма `/admin/redirects/new` читает `from` из адреса страницы.

## Ошибки и безопасность

- Ошибка синхронизации ловится в воркере, пишется в журнал и в лог без тела запроса; тело ответа обрезается до 300
  символов, как в `metrika/client.ts`. Токен не попадает ни в журнал, ни в ответы API.
- Регулярное выражение бренда применяется в SQL через параметр (`~*` с `$1`), не склейкой строки.
- Разделы и эндпоинты — только роль admin; редактор получает 403 и не видит пункта меню.
- Персональных данных в новых таблицах нет: только агрегаты и адреса страниц сайта.

## Тесты

vitest на своей одноразовой базе (`TEST_DATABASE_URL`), внешние API — внедрённый `fetch`.

- Клиенты: разбор ответа Метрики (в том числе `sampled=true` → ошибка), постраничный `query-analytics`, 429 с
  `Retry-After`, 420, 401, 403 `INVALID_USER_ID`, 404 `HOST_NOT_VERIFIED`.
- Синхронизация: повторный запуск не дублирует строки; окно 7 дней перезаписывает значения; ошибка Вебмастера не мешает
  Метрике; первый запуск берёт историю; снимок адресов заменяется целиком.
- Воркер: не запускается без флага, токена или вне production; пропускает источник, синхронизированный меньше 20 часов
  назад.
- `growth.ts`: каждое правило на заготовленных строках, граничные значения порогов, бренд отсекается.
- `queries.ts`: заказ без атрибуции не ломает таблицу страниц; удалённые и неоплаченные заказы не считаются в выручке.
- API: роль editor получает 403; неверный период — 400.
- Витрина: страница 404 отправляет `not_found` один раз.

   `webmaster:verify`; выпустить токен от аккаунта, у которого есть доступ к счётчику 113445304 и к сайту в Вебмастере.

3. Запустить пробный скрипт на сервере (команда будет в описании PR 1) и прислать вывод — по нему фиксируются имена
   измерений.
4. Раз в 6 месяцев перевыпускать токен (когда токен перестанет работать, в админке появится плашка).
