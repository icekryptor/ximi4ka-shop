# Яндекс Пэй и Сплит на сайте — дизайн

Дата: 2026-10-24. Ветка: `claude/yandex-pay-split-integration-72a27a`.

Продолжает незавершённую работу от 11.10.2026 (worktree `jolly-panini-f53f95`, ветка `claude/yandex-pay-integration-a0e6c6`,
не закоммичена, в main её нет). Её спек `2026-10-11-yandex-pay-design.md` лежит только в том worktree. Всё, что из него
сохраняется, повторено здесь, так что этот документ самодостаточен.

## Цель

Покупатель оплачивает заказ через Яндекс Пэй — картой или частями в Сплите — и видит возможность оплатить частями ещё до
чекаута: на карточке товара и в корзине. Т-Касса остаётся основным способом.

Критерии успеха:

- пока `PAYMENT_PROVIDERS` не задан, прод ведёт себя как сейчас: мёрж ничего не меняет для покупателей;
- в песочнице Яндекса проходит полный цикл и картой, и Сплитом: заказ → форма Яндекса → оплата → статус «оплачен»;
- сумма корзины, переданной Яндексу, равна итогу заказа при промокоде, оптовой скидке и любой доставке;
- потерянный вебхук добирается сверкой, в том числе после выключения способа;
- скрипт Яндекса не ухудшает заметно INP и FCP карточки товара (замер `tools/perf-lab` до и после);
- ключей нет ни в репозитории, ни в публичных ответах API.

## Принятые решения

| Вопрос            | Решение                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| Охват             | Оплата на чекауте плюс плашки Сплита на карточке товара и в корзине (страница и боковая). Каталог — позже |
| Интеграция оплаты | Сервер создаёт заказ в Yandex Pay API, покупатель уходит на `paymentUrl`. Кнопку SDK не используем        |
| Скрипт Яндекса    | `pay.js` только для бейджей и виджета; оплата от него не зависит                                          |
| Чекаут            | Три пункта: «Картой — Т-Банк» (по умолчанию), «Яндекс Пэй», «Сплит — оплата частями» с виджетом графика   |
| Сплит             | Тот же заказ Яндекса с `preferredPaymentMethod: 'SPLIT'`; карта в форме остаётся запасным вариантом       |
| Чеки 54-ФЗ        | Облачная касса (АТОЛ Онлайн или CloudKassir), подключённая в кабинете Яндекса; мы передаём налог позиций  |
| Доставка в ЕАЭС   | Пункты Яндекса скрыты, чекаут для этих стран не меняется                                                  |
| Основа кода       | Работа от 11.10 переносится на свежий main вручную, с правками под промокод, YCP и ЕАЭС                   |

## Не входит в задачу

- возвраты, отмена и списание через API Яндекса (`REFUND`, `VOID`, `CAPTURE`), двухстадийная оплата, Сплит «при получении»;
- бейджи в каталоге и на главной;
- брендированная кнопка Яндекс Пэй (Web SDK `PaymentButton`);
- отметка, чем именно заплатил покупатель (картой или Сплитом): в админке провайдер подписан просто «Яндекс Пэй»;
- отправка чеков нашим сервером: их пробивает касса, подключённая в кабинете Яндекса;
- включение на проде: мёрж выкатывает код, переменные в `deploy/app.env` и настройки кабинета вносит владелец.

## Текущее состояние main

- `api/src/lib/payments/`: провайдеры `manual` и `tbank`. `getPaymentProvider()` в `index.ts` выбирает один провайдер на весь
  магазин по `PAYMENT_PROVIDER`. Вебхук `routes/webhooks/tbank.ts` всегда создаёт `TBankProvider`.
- `shared/src/types/order.ts:13`: `PaymentProvider = 'manual' | 'tbank' | 'ycp'`; `'ycp'` — заказы «Купить в 1 клик», у них
  нет класса-провайдера, сверка их пропускает. Колонка `orders.payment_provider` — строка, миграция не нужна.
- `receipt.ts` с 8c4104d раскидывает промокод по позициям (`spreadDiscount`); работа от 11.10 об этом не знает.
- `SiteSettings.yandexPayEnabled` и `yandexPayMode` есть в базе и в админке (`SettingsForm.tsx:309-334`), кодом не используются;
  публичный `GET /api/public/settings` их намеренно не отдаёт.
- `api/src/app.ts:76` — глобальный `express.json`, сырого тела для вебхуков нет. Зависимости `jose` нет.
- CSP и `Cross-Origin-Opener-Policy` нигде не заданы (ни в Next, ни в Caddy), то есть требований SDK Яндекса ничто не нарушает.
- Спек CloudPayments (`2026-10-17-cloudpayments-card-payments-design.md`) тоже вводит `paymentMethod` на чекауте и выбор
  провайдера по заказу; реестр ниже сделан так, чтобы CloudPayments встал в него ещё одним провайдером.

## Конфигурация

| Переменная                    | Назначение                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| `PAYMENT_PROVIDERS`           | включённые онлайн-провайдеры через запятую: `tbank`, `yandex_pay`                           |
| `PAYMENT_PROVIDER`            | прежняя переменная; действует, только если `PAYMENT_PROVIDERS` пуста                        |
| `YANDEX_PAY_MERCHANT_ID`      | идентификатор продавца; в песочнице он же ключ API; сверяется с `merchantId` вебхука        |
| `YANDEX_PAY_API_KEY`          | ключ API боевого режима (`Authorization: Api-Key …`)                                        |
| `YANDEX_PAY_PAYMENT_METHODS`  | методы формы, по умолчанию `CARD,SPLIT`; без `SPLIT` пункт «Сплит» и плашки не показываются |
| `YANDEX_PAY_SANDBOX_CHECKOUT` | `true` показывает песочницу покупателям; только на время проверки на сервере                |

В админке: `yandexPayEnabled` — рубильник без перезапуска (выключен → способы Яндекса и плашки скрыты, вебхук и сверка
продолжают работать), `yandexPayMode` — `sandbox` или `production`.

Правила разбора — как в работе от 11.10: пустая строка считается незаданной (docker-compose отдаёт `KEY=`), неизвестное имя
логируется и пропускается, провайдер без ключей при старте отбрасывается с записью в лог.

## Сервер

### Реестр провайдеров (`api/src/lib/payments/index.ts`)

- `getCheckoutProviders()` — провайдеры, которые можно предложить на чекауте: включены в `PAYMENT_PROVIDERS`, настроены,
  для Яндекса ещё `yandexPayEnabled` и правило песочницы. Пустой список → `manual`, как сейчас.
- `getProviderByName(name)` — провайдер заказа для вебхука и сверки. Ищет среди **настроенных** (заданы ключи), а не среди
  включённых: после отката (`yandex_pay` убран из списка) уже созданные заказы Яндекса досверяются.
- `PaymentProvider.verifyAndParseWebhook` становится асинхронным и принимает `{ body, rawBody }`: Т-Касса читает `body`,
  Яндекс — `rawBody`. Поведение Т-Кассы не меняется, её тесты адаптируются под сигнатуру.

### Адаптер `yandexPay.ts`

- `createPayment(order, { preferSplit })` — `POST {base}/api/merchant/v1/orders`, `base` = `https://pay.yandex.ru` или
  `https://sandbox.pay.yandex.ru` по `yandexPayMode`. Тело: `orderId` (номер заказа, он же ключ идемпотентности),
  `currencyCode: 'RUB'`, `cart`, `availablePaymentMethods` из `YANDEX_PAY_PAYMENT_METHODS`, `preferredPaymentMethod: 'SPLIT'`
  при выборе Сплита, `redirectUrls` (`onSuccess`, `onError`, `onAbort` — страница заказа с публичным токеном, как у Т-Кассы),
  `fiscalContact` (email, иначе телефон). Ответ `data.paymentUrl` → `{ externalId: orderNumber, paymentUrl }`; любой сбой
  логируется с телом ответа Яндекса и даёт `null`, как у Т-Кассы.
- `getStatus(externalId)` — `GET /api/merchant/v1/orders/{orderId}`; `CAPTURED`/`CONFIRMED` → `paid`, `FAILED`/`VOIDED` →
  `failed`, остальное → `pending`, ошибка → `unknown`.

### Корзина Яндекса (`yandexCart.ts`, `orderLines.ts`)

Общий построитель позиций `orderLines.ts` выносится из `receipt.ts` и **включает раскидку промокода** (`spreadDiscount` из
main) с пропуском позиций, ставших нулевыми. Формат Т-Кассы (`receipt.ts`) и формат Яндекса (`yandexCart.ts`) строятся из
него раздельно.

- суммы — строки в рублях, цена за единицу не больше двух знаков после запятой (иначе `ORDER_CART_DATA_ERROR`); цена, не
  делящаяся на копейки, разбивается на две позиции, как уже делает `receipt.ts`;
- доставка — отдельная позиция, подарки пропускаются, `productId` уникальны;
- у каждой позиции `receipt.tax` по таблице кодов Яндекса из тех же настроек чека, что у Т-Кассы (`TBANK_RECEIPT_TAX`);
- инвариант: сумма позиций равна `order.totalRub`, иначе заказ в Яндекс не отправляется и в лог пишется расхождение.

### Вебхук `POST /api/webhooks/yandex-pay/v1/webhook`

Яндекс дописывает `/v1/webhook` к Callback URL сам, поэтому в кабинете указывается `https://ximi4ka.ru/api/webhooks/yandex-pay`.

- маршрут монтируется до `express.json` с `express.raw({ type: '*/*', limit: '64kb' })`;
- тело — JWT ES256; ключ по `kid` из JWKS (`https://pay.yandex.ru/api/jwks` или `https://sandbox.pay.yandex.ru/api/jwks` по
  режиму, адрес никогда не берётся из запроса); проверяются `alg`, `exp`, `iat` и `merchantId` = `YANDEX_PAY_MERCHANT_ID`;
  JWKS кешируется, при неизвестном `kid` кеш сбрасывается один раз; библиотека `jose`;
- обрабатывается `ORDER_STATUS_UPDATED`: `CAPTURED`/`CONFIRMED` → `paid`, `FAILED`/`VOIDED` → `failed`, прочие статусы — 200 без
  изменений; неизвестный заказ — 200;
- ошибка проверки — не-200 с `{ status: 'fail', reasonCode, reason }` (`UNAUTHORIZED`, `TOKEN_EXPIRED`, `OTHER`), успех —
  `200 {"status":"success"}`; повтор того же события безопасен (`applyPaymentStatus` идемпотентен);
- дальше как у Т-Кассы: `applyPaymentStatus(order, status, 'yandex_pay')` и `saveOrderWithStatusEvent` — уведомления, выдача
  материалов и офлайн-конверсии Метрики срабатывают без доработок.

### Сверка

`reconcilePendingOrders` берёт провайдера по `order.paymentProvider` через `getProviderByName`, заказы `ycp` и `manual`
пропускает. Задача сверки запускается, если настроен хотя бы один онлайн-провайдер.

### Чекаут API

- `GET /api/public/payment-methods` → `{ methods: ('tbank' | 'yandex_pay' | 'yandex_split')[], yandexPay?: { merchantId } }`.
  `yandex_split` есть, только если включён Яндекс и в методах есть `SPLIT`. `merchantId` отдаётся **только в боевом режиме**:
  в песочнице он равен ключу API. Ответ кешируется на 60 секунд.
- `POST /checkout` принимает необязательный `paymentMethod`:
  - нет — первый из доступных;
  - не входит в доступные — `400`;
  - `yandex_pay` или `yandex_split` при доставке `cdek_manual_cis` — `400`: правило ЕАЭС проверяется и на сервере;
  - в базу пишется провайдер (`yandex_pay` для обоих вариантов Яндекса); повтор с тем же ключом идемпотентности
    возвращает сохранённый `paymentUrl`.

### Типы и админка

- `shared`: `PaymentProvider = 'manual' | 'tbank' | 'ycp' | 'yandex_pay'`; онлайн-провайдеры чекаута — `'tbank' | 'yandex_pay'`
  (`ycp` и `manual` исключены явно); актор истории `by` дополняется `'yandex_pay'`.
- `web/app/admin/(authed)/orders/orderUi.ts`: подпись «Яндекс Пэй», отличная от «Яндекс (YCP)».

## Витрина

### Плашки Сплита

Клиентский компонент `web/components/payments/SplitBadge.tsx`:

- рисует `<yandex-pay-badge type="bnpl" amount merchant-id source size>` (тип для JSX объявляется вручную, npm-пакета у Яндекса нет);
- подключает `https://pay.yandex.ru/sdk/v1/pay.js` через `next/script` с `id="yandex-pay-sdk"` и `strategy="lazyOnload"`, как
  счётчики в `web/lib/analytics.tsx`; скрипт подключается один раз на страницу;
- ничего не рисует без `merchantId` или без `yandex_split` в списке способов;
- резервирует высоту строки бейджа, чтобы контент под ним не прыгал; если Сплит покупателю недоступен, бейдж скрывает сам
  Яндекс и остаётся пустой отступ.

Места:

- карточка товара `product/[slug]/page.tsx` — под рядом «цена + В корзину» (:287-293), `source="item"`, сумма = `priceRub`;
- страница корзины `cart/page.tsx` — под «Итого» (:102-103), `source="cart"`, сумма = `totals.totalRub`;
- боковая корзина `CartDrawer.tsx` — под «Итого» (:216-217), бейдж монтируется только у открытой корзины, чтобы скрипт не
  грузился на каждой странице сайта.

Список способов витрина получает с `GET /api/public/payment-methods`. Серверная карточка товара — при рендере, клиентские
корзины — одним запросом с кешем на время сессии.

### Чекаут

Блок «Способ оплаты» в `checkout/page.tsx` перед итогами (около :469), разметка по образцу «Куда доставить» (`fieldset`,
`legend`, радиокнопки):

- «Картой — Т-Банк» (по умолчанию; если Т-Касса принимает СБП, подпись «Картой или СБП — Т-Банк»), «Яндекс Пэй»,
  «Сплит — оплата частями» с бейджем `source="checkout"` на сумму заказа;
- при выбранном Сплите под пунктом монтируется виджет Ultimate (`YaPay.createSession` с `merchantId`, `totalAmount`,
  `availablePaymentMethods: ['SPLIT']`, `version: 4`; `mountWidget` без своей кнопки оплаты); без скрипта остаётся текст;
- блок показывается при двух и более способах; при одном чекаут выглядит как сейчас;
- при выборе доставки в ЕАЭС пункты Яндекса скрываются, выбор сбрасывается на Т-Банк;
- выбранный способ уходит в `POST /checkout` как `paymentMethod`, переход на `paymentUrl` — как сейчас;
- логотипы Пэй и Сплита — только официальные из бренд-кита Яндекса без изменений; нет файлов — текстовые подписи.

### Страница заказа

`OrderStatusView` для неоплаченного заказа Яндекса показывает «Оплатить» со ссылкой Яндекса — как в работе от 11.10.

## Безопасность

- ключи только в `deploy/app.env` на сервере и в локальном `api/.env` разработчика; в репозитории — плейсхолдеры в
  `deploy/app.env.example` и `api/.env.example`;
- публичные ответы не содержат ключей и песочничного Merchant ID;
- вебхук отказывает при любой неудачной проверке и при незаданном `YANDEX_PAY_MERCHANT_ID`; JWKS только с хостов Яндекса;
  размер тела ограничен;
- сумма платежа считается только на сервере из заказа; клиент передаёт лишь `paymentMethod`;
- перед PR — `/security-review`;
- ключи, показанные в чате 11.10, перевыпустить в кабинете после запуска.

## Проверка в песочнице

1. **Локально, без вебхука.** Владелец вписывает песочничный Merchant ID в локальный `api/.env`. Заказ с чекаута → форма
   песочницы → оплата тестовой картой «Мир»; второй заказ — Сплитом. Сверка (`getStatus`) переводит оба в «оплачен».
   Проверяются API, корзина, поля чека, открытие формы на Сплите. Сумма 10 001 ₽ даёт `FAILED` — проверка отказа.
2. **Живой вебхук.** Вариант по решению владельца на этом этапе: временный туннель (cloudflared) на локальный API, на который
   владелец на время теста направляет песочничный Callback URL в кабинете, — прод не затрагивается. Иначе — на сервере после
   мёржа: `yandexPayMode=sandbox` и `YANDEX_PAY_SANDBOX_CHECKOUT=true` на короткое окно по команде владельца, затем выключить.
3. **Плашки и скорость.** Локально с боевым Merchant ID (он публичный) и `yandexPayMode=production` без ключа API: бейджи на
   карточке, в корзинах и на чекауте, виджет Сплита; замер `tools/perf-lab` (INP, FCP карточки товара) до и после.

## Выкатка

1. PR, ревью, мёрж по команде владельца. `PAYMENT_PROVIDERS` не задан → у покупателей ничего не меняется.
2. Владелец: подключает облачную кассу в кабинете Яндекса, указывает боевой Callback URL, вписывает в `deploy/app.env`
   `YANDEX_PAY_MERCHANT_ID`, `YANDEX_PAY_API_KEY`, перезапускает api.
3. В админке `yandexPayMode=production`, `yandexPayEnabled=true`, в `app.env` `PAYMENT_PROVIDERS=tbank,yandex_pay` →
   появляются способы оплаты и плашки.
4. Первый настоящий платёж на небольшую сумму: статус заказа, пришедший чек, Telegram-карточка; возврат вручную в кабинете.
5. Откат: выключить `yandexPayEnabled` в админке (мгновенно) или убрать `yandex_pay` из `PAYMENT_PROVIDERS`; созданные заказы
   Яндекса досверяются.

## Риски и открытые вопросы

- **Категории.** Правила Яндекса запрещают яды, прекурсоры и сильнодействующие вещества. Заявка одобрена, но новые реактивы
  стоит сверять с `pay.yandex.ru/docs/ru/forbidden`.
- **Код налога.** Таблица кодов Яндекса: ставка 20% с 2026 года заменена кодом 11 (22%), в OpenAPI перечислены только 1–10.
  Магазин без НДС (код 6), но значение проверить в песочнице.
- **СБП у Т-Кассы** — уточнить, чтобы подпись пункта была правдивой.
- **Акционные тарифы** Яндекса (0,1% на карты, 3,5% на Сплит до 31.12.2026) заявлены для «формы заказа»; распространяются ли
  они на оплату по API — вопрос к менеджеру Яндекса, на код не влияет.
