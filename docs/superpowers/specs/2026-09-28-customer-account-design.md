# Личный кабинет покупателя — дизайн

**Дата:** 28.09.2026. **Статус:** дизайн согласован по частям, ждёт просмотра спеки.

## 1. Зачем

Покупатель хочет видеть свои заказы и не вводить контакты заново при каждой
покупке. Сейчас аккаунтов у покупателей нет: заказ открывается только по ссылке
с секретом, а контакты живут в каждом заказе отдельно.

**Готово, когда:** покупатель входит по коду из письма или через Telegram-бота
без пароля и отдельной регистрации; в кабинете видит все свои заказы (новые и
прошлые с тем же подтверждённым email) и может поправить имя и телефон; на
чекауте контакты и доставка подставляются сами; из кабинета одним нажатием
пишет в поддержку @ximi4ka_support. Оформить заказ без аккаунта можно
по-прежнему.

## 2. Решения (согласованы 28.09.2026)

| Вопрос              | Решение                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------ |
| Вход по email       | 6-значный код на почту, без паролей. Регистрация = первый вход                                   |
| Почта               | SMTP ящика домена (noreply@ximi4ka.ru) через nodemailer                                          |
| Вход через Telegram | Через бота: deep link `?start=<nonce>` + кнопка «Подтвердить вход» в чате, webhook в api         |
| Бот                 | Новый покупательский бот, отдельный токен. Служебный @ximsite_bot не трогаем                     |
| История заказов     | Заказы из аккаунта + прошлые заказы с тем же **подтверждённым** email. По телефону и @нику — нет |
| Личные данные       | Имя, телефон, email, Telegram; привязка второго способа входа; автозаполнение чекаута            |
| Где живёт auth      | В Express api по образцу админки: сессия в базе, HttpOnly-cookie, CSRF double-submit             |

Отвергнуто: Telegram Login Widget (привязан к одному домену, на мобильных
просит телефон во всплывающем окне), Auth.js в Next (нет нужных провайдеров,
auth оторвался бы от данных), JWT без сессий (нельзя отозвать, мешает слиянию
аккаунтов), адресная книга (лишняя работа в чекауте со СДЭК; хватает доставки
из последнего заказа).

## 3. Данные

Одна миграция TypeORM, новые сущности регистрируются в
`api/src/config/dataSource.ts`.

### `customers`

| Поле                | Тип                  | Примечание                                                             |
| ------------------- | -------------------- | ---------------------------------------------------------------------- |
| `id`                | uuid PK              |                                                                        |
| `email`             | text, nullable       | уникальный по `lower(email)`; пишется только после подтверждения кодом |
| `telegram_id`       | bigint, nullable     | уникальный                                                             |
| `telegram_username` | text, nullable       | без `@`, обновляется при каждом входе через Telegram                   |
| `name`              | text, nullable       |                                                                        |
| `phone`             | text, nullable       | не подтверждён, используется только для автозаполнения                 |
| `created_at`        | timestamptz          |                                                                        |
| `last_login_at`     | timestamptz nullable |                                                                        |

Ограничение: хотя бы одно из `email`, `telegram_id` не NULL.

### `customer_sessions`

Копия `admin_sessions`: `id`, `customer_id` FK (on delete cascade),
`token_hash` (sha256, уникальный), `expires_at` (60 дней), `revoked_at`,
`ip`, `user_agent`, `created_at`.

### `customer_email_codes`

`id`, `email` (в нижнем регистре), `code_hash` (sha256 от `id + code`),
`expires_at` (10 минут), `attempts` (int, максимум 5), `consumed_at`,
`link_customer_id` (nullable — код запрошен из кабинета для привязки email),
`created_at`. Индекс по `(email, created_at)` для лимитов отправки.

### `telegram_login_requests`

`id`, `nonce_hash` (уникальный), `poll_secret_hash`, `status`
(`pending` → `confirmed` → `consumed`), `telegram_id`, `telegram_username`,
`telegram_first_name`, `link_customer_id` (nullable), `expires_at` (10 минут),
`created_at`.

`nonce` — 32 байта base64url (43 символа, укладывается в лимит 64 символа
параметра `start`). `poll_secret` — отдельный случайный токен, живёт только в
HttpOnly-cookie браузера, который начал вход.

### `orders.customer_id`

Nullable FK на `customers` (on delete set null), индекс. Существующее поле
`customer_email` остаётся как есть; пустое значение `''` ни с чем не совпадает.

## 4. Авторизация

### Cookie

- `ximi4ka_customer_session` — HttpOnly, SameSite=lax, Secure в проде, 60 дней.
- `ximi4ka_customer_csrf` — читаемая, для заголовка `X-CSRF-Token`.
- `ximi4ka_customer_tg_poll` — HttpOnly, 10 минут, `poll_secret` входа через
  Telegram.

Имена не пересекаются с админскими — это независимые сессии. Middleware
`requireCustomerAuth` и `requireCustomerCsrf` устроены как
`requireAdminAuth` / `requireCsrfToken`.

### Вход по email

1. `POST /api/account/auth/email/start {email}` — нормализует email, создаёт
   код, шлёт письмо «Код для входа на ximi4ka.ru: 123456». Ответ всегда
   `204`, не раскрывает, есть ли аккаунт. Лимиты: 1 письмо на адрес в 60 с,
   5 в час; по IP — 20 в час.
2. `POST /api/account/auth/email/verify {email, code}` — берёт последний
   неиспользованный неистёкший код для адреса, сравнивает хэш через
   `timingSafeEqual`. Ошибка — `400 {code: 'invalid_code', attemptsLeft}`;
   исчерпаны попытки или истёк — `400 {code: 'code_expired'}`. Успех: код
   помечен `consumed_at`, покупатель найден по `lower(email)` или создан,
   выставлена сессия, `last_login_at` обновлён, выполнена подтяжка заказов
   (п. 4.4).

### Вход через Telegram

1. `POST /api/account/auth/telegram/start` — создаёт запрос, ставит cookie
   `ximi4ka_customer_tg_poll`, отвечает `{deepLink: 'https://t.me/<бот>?start=<nonce>'}`.
2. Пользователь жмёт «Старт». Telegram шлёт update на
   `POST /api/telegram/login-webhook`; api сверяет заголовок
   `X-Telegram-Bot-Api-Secret-Token` с `TELEGRAM_LOGIN_WEBHOOK_SECRET`
   (несовпадение — `401`). Для `/start <nonce>` бот отвечает сообщением
   «Войти на сайт ximi4ka.ru?» с inline-кнопкой **«Подтвердить вход»**
   (`callback_data` = id запроса). Кнопка обязательна: без неё злоумышленник
   может прислать жертве свою ссылку и после «Старт» оказаться в её аккаунте.
3. `callback_query` с этим id от того же `from.id`, что нажал «Старт» →
   запрос `confirmed`, сохранены `telegram_id`, username, имя; бот
   редактирует сообщение на «Готово, вернитесь на сайт».
4. Сайт раз в 2 с опрашивает `GET /api/account/auth/telegram/status`
   (по cookie). `pending` → `{status: 'pending'}`; `confirmed` → запрос
   `consumed`, покупатель найден по `telegram_id` или создан, выставлена
   сессия, cookie опроса удалена, `{status: 'ok'}`; истёк → `{status: 'expired'}`.

Webhook всегда отвечает Telegram `200` (кроме неверного секрета), чтобы он не
повторял update. Неизвестный или истёкший nonce — бот пишет «Ссылка устарела,
начните вход на сайте заново». Прочие сообщения боту — короткая подсказка со
ссылкой на сайт и на @ximi4ka_support.

Клиент бота — отдельный экземпляр поверх существующего `fetch`-клиента
`api/src/lib/telegram/bot.ts` (добавляются `sendMessage` с `reply_markup`,
`answerCallbackQuery`, `editMessageText`, `setWebhook`). Установка webhook —
скрипт `npm run telegram:set-webhook -w api` (URL, секрет,
`allowed_updates: ['message', 'callback_query']`).

### Подтяжка прошлых заказов

После входа по email и после привязки email:

```sql
UPDATE orders SET customer_id = :id
WHERE customer_id IS NULL AND customer_email <> '' AND lower(customer_email) = :email
```

По телефону и @нику не привязываем — они не подтверждены, опечатка открыла бы
чужой адрес и телефон.

### Привязка второго способа и слияние аккаунтов

Из кабинета запускается тот же поток с `link_customer_id` = текущий покупатель
(эндпоинты под `requireCustomerAuth` + CSRF: `POST /api/account/link/email/start`,
`/link/email/verify`, `/link/telegram/start`, `/link/telegram/status`).

- Email/Telegram ни к кому не привязан → записывается в текущий аккаунт.
- Уже принадлежит другому аккаунту → **слияние** в одной транзакции: заказы
  другого аккаунта переезжают в текущий, пустые поля текущего заполняются из
  другого, сессии другого отзываются, другой удаляется. Безопасно: пользователь
  только что доказал владение обоими способами.
- После привязки email — подтяжка заказов.

Отвязка (`POST /api/account/email/unlink`, `/telegram/unlink`) разрешена,
только если остаётся второй способ входа, иначе `409 last_login_method`.

### Выход

`POST /api/account/auth/logout` — отзывает текущую сессию, чистит cookie.
«Выйти со всех устройств» — не в этой версии.

## 5. API кабинета

Все под `requireCustomerAuth`; изменяющие — ещё под CSRF.

| Метод и путь                   | Что делает                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| `GET /api/account/auth/config` | Публичный. `{email: bool, telegram: bool, telegramBot: 'имя'}` — какие способы входа включены |
| `GET /api/account/me`          | Профиль + `lastDelivery` (способ, город, код ПВЗ или адрес курьера) из последнего заказа      |
| `PATCH /api/account/me`        | `{name?, phone?}` с теми же правилами валидации, что в чекауте                                |
| `GET /api/account/orders`      | Заказы покупателя, новые сверху, `?cursor=` по 20. Поля ниже                                  |

Поля заказа в списке: `orderNumber`, `createdAt`, `status`, `totalRub`,
первые позиции (название, картинка, количество) и их общее число, трек СДЭК
если есть, `publicToken`. Фильтр строго по `customer_id` сессии.

## 6. Web

Все страницы под `web/app/[locale]/(public)/account/` — шапка и подвал
общие с магазином.

### `/account/login`

- Два варианта: «Войти по почте» и «Войти через Telegram» (кнопка скрыта,
  если бот не настроен; при выключенной почте — пояснение «Вход по почте
  временно недоступен»).
- Почта: поле email → шаг кода из 6 полей (вставка всего кода, автопереход),
  «Отправить ещё раз» с таймером 60 с, «Изменить email», текст ошибки с
  оставшимися попытками.
- Telegram: кнопка открывает `deepLink` в новой вкладке/приложении, рядом
  состояние «Ждём подтверждения в Telegram…» с опросом статуса; «истекло» →
  «Начать заново».
- Мелкий текст: «Продолжая, вы соглашаетесь с политикой обработки
  персональных данных» со ссылкой.
- После входа — переход на `?next=` (только относительный путь, начинается с
  `/`, не с `//`), по умолчанию `/account`. Уже залогиненного сразу ведёт туда же.

### `/account`

Layout на сервере зовёт `GET /api/account/me` с пересланной cookie; 401 —
редирект на `/account/login?next=…`. Два раздела: вкладки слева на десктопе,
сверху на мобильном.

- **Заказы** (по умолчанию): карточки — номер, дата, статус чипом, сумма,
  превью позиций, трек СДЭК. Клик — существующая страница
  `/order/N#t=<publicToken>`. «Показать ещё» по курсору. Пусто — «Здесь
  появятся ваши заказы» и кнопка в каталог.
- **Личные данные**: имя и телефон — форма с сохранением; email — показ,
  «Изменить»/«Привязать» через код; Telegram — показ `@username`,
  «Привязать»/«Отвязать»; «Выйти».
- **Поддержка**: на обеих вкладках заметная кнопка «Написать в поддержку» →
  `https://t.me/ximi4ka_support`.

### Шапка и меню

Иконка профиля рядом с `CartButton` в `web/components/Header.tsx` — ссылка на
`/account` (статус сессии в шапке не нужен, решает layout). В
`MobileMenuOverlay` — пункт «Личный кабинет».

### Чекаут

- Запрос `POST /api/checkout` уходит с cookie (`credentials: 'include'`);
  api, найдя действующую сессию, пишет `customer_id`. CSRF не нужен —
  SameSite=lax не отправит cookie в кросс-сайтовом POST.
- Если в профиле пусто — имя и телефон заполняются из этого заказа.
- Заказ без сессии, но с email, совпадающим с подтверждённым email аккаунта,
  тоже привязывается к нему.
- Автозаполнение для залогиненного: имя, телефон, email, Telegram — если поле
  пустое; способ доставки из `lastDelivery`: ПВЗ выбирается по коду после
  загрузки списка точек (исчезла — пользователь выбирает заново), курьеру
  подставляется адрес. Город уже хранится в localStorage — не меняется.
- Незалогиненным — строка под формой «Войдите, чтобы заказ сохранился в
  кабинете» со ссылкой на `/account/login?next=/checkout`.

## 7. Ошибки и деградация

- **SMTP не задан:** в проде `email/start` → `503 email_login_unavailable`,
  `auth/config` отдаёт `email: false`. В dev и тестах — log-транспорт: код в
  pino и в памяти процесса (тесты читают оттуда). Сбой SMTP → `502`, код уже
  создан, повторная отправка работает.
- **Бот не задан:** `auth/config` отдаёт `telegram: false`, кнопка скрыта,
  эндпоинты Telegram → `503`.
- **Сессия истекла:** `/account` → логин с `?next=`; на чекауте 401 от `/me`
  просто означает гостевой заказ.
- **Ошибки слияния** — транзакция откатывается, `500`, пользователь остаётся в
  текущем аккаунте.

## 8. Безопасность

- В базе только sha256-хэши токенов сессий, кодов, nonce и `poll_secret`.
- Rate limit (существующий in-memory `rateLimit`) на `email/start`,
  `email/verify`, `telegram/start`, `telegram/status`, webhook.
- `callback_query` подтверждает вход, только если его прислал тот же
  Telegram-пользователь, что и `/start`.
- `/orders` фильтрует строго по `customer_id` сессии.
- В логах email маскируется (`a***@mail.ru`); коды не логируются нигде, кроме
  log-транспорта в dev.
- Перед мёржем — `/security-review`.

## 9. Env и эксплуатация

Новые переменные в `api/.env.example` и `deploy/app.env.example`:
`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`,
`MAIL_FROM`, `TELEGRAM_LOGIN_BOT_TOKEN`, `TELEGRAM_LOGIN_BOT_USERNAME`,
`TELEGRAM_LOGIN_WEBHOOK_SECRET`. В web новых переменных нет — конфиг из
`auth/config`.

`deploy/README.md` — раздел: создать бота в BotFather (имя, аватар,
описание), прописать env, выполнить `telegram:set-webhook`, настроить SPF и
DKIM для домена почты.

## 10. Тесты

**api** (vitest + supertest + настоящая Postgres):

- email-поток: старт → код из log-транспорта → вход → повторный вход тем же
  аккаунтом; лимит отправки; 5 неверных попыток; истёкший код; использованный
  код повторно не работает;
- Telegram-поток на фейковом клиенте бота: start → webhook `/start` →
  callback «Подтвердить» → status `ok` → сессия; неверный секрет webhook;
  чужой `from.id` в callback; истёкший nonce;
- подтяжка заказов: только по совпадающему email, `''` не совпадает, уже
  привязанные к другому не перехватываются;
- привязка и слияние аккаунтов, отвязка последнего способа → 409;
- `/orders`: покупатель не видит чужих заказов; пагинация;
- чекаут с сессией пишет `customer_id`, без сессии — нет.

**web** (vitest + Testing Library): форма логина (шаги email и кода,
ожидание Telegram, скрытие выключенных способов), список заказов и пустое
состояние, форма личных данных, автозаполнение чекаута, иконка в шапке,
проверка `next`.

**Вручную:** локально в браузере — вход по коду из log-транспорта, кабинет,
чекаут. Telegram — на проде после установки webhook (до localhost бот не
достучится).

## 11. Не в этой версии

Адресная книга, «выйти со всех устройств», уведомления покупателю о статусах
заказа в Telegram (бот это позволит, но отдельной задачей), подтверждение
телефона, удаление аккаунта из интерфейса.
